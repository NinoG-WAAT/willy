# Interface language (English and French)

Package 1 of the French umbrella (#113), built in #114. This is the reference for everyone who converts a screen. The decisions are fixed; if one has to change, change this file in the same PR and say why.

## 1. How it works in one minute

- **Gettext style.** The English text is the key: `t("Sign in")`. In English it returns the text unchanged, so every English test keeps passing. In French it looks the text up in the French catalog.
- **Catalogs** are plain `Record<string, string>` modules, one per area, in `src/i18n/fr/<area>.ts`, merged by `src/i18n/fr/index.ts`.
- **Locale of a request** = the signed-in owner's choice (`settings.language`), else the server default `WILLY_DEFAULT_LOCALE` (default `en`). Signed-out pages use the default. The middleware `language` (`src/middleware.ts`, after `auth`) sets it once per request.
- **Anywhere in a request** (pages, components, use cases, domain functions) `t()` just works: nothing passes a locale around.
- **Safety nets.** A unit test (`tests/unit/i18n/catalog.test.ts`) fails when a `t()` literal has no French entry, when a French entry is unused, when `{params}` differ, and a few more things (section 8). `WILLY_I18N_STRICT=1` makes the server throw on a missing French string, so a crawl of every screen in French fails loudly.

## 2. The API (`src/i18n/translate.ts`, pure TypeScript)

```ts
import { t, tn, msg, currentLocale, parseLocale, type Locale } from "../i18n/translate";
// In a client script: import from "./i18n" or "../i18n" (src/scripts/i18n.ts), same names.

t("Sign in");                                   // "Sign in" / "Se connecter"
t("Hello {name}", { name: owner.displayName }); // {name} filled in; a missing param stays visible, never throws
tn("{n} note", "{n} notes", count);             // plural; {n} is added automatically and formatted for the locale
msg("Draft");                                   // marks a string for extraction, returns it unchanged (section 5)
currentLocale();                                // "en" | "fr" for the request being served
parseLocale(raw);                               // "en" | "fr" | null (exact codes only; never guesses from "fr-FR")
```

| Export | Use |
|---|---|
| `t(source, params?)` | one sentence or label. `params`: `Record<string, string \| number>`, referenced as `{name}` |
| `tn(one, many, n, params?)` | plural. Both English forms are given and both contain `{n}`. They are two ordinary catalog keys, translated independently. English: `one` only for exactly 1. French: `one` for 0 and 1 (and anything under 2), `many` from 2 |
| `msg(source)` | extraction marker, see section 5 |
| `currentLocale()`, `Locale`, `LOCALES`, `parseLocale()` | the locale type and helpers. `Locale = "en" \| "fr"` |
| `intlLocale(locale?)` | the `Intl` tag: `en` is `en-GB`, `fr` is `fr-FR` |
| `formatNumber(n, locale?)` | `Intl.NumberFormat` for the locale |
| `MissingTranslationError` | thrown in strict mode |

Wiring functions (`setLocaleResolver`, `registerCatalog`, `configureI18n`, `placeholderNames`) exist for start-up and for tooling. Screens never call them.

`t()` returns **plain text**. Render it as a text node (`{t("...")}` in Astro, `textContent` in a script). Never `set:html`, never `innerHTML` (section 7).

### Placeholders

- `{name}`: letters, digits and `_`, starting with a letter or `_`. Filled in one pass: a value is inserted literally and never re-scanned (`$&`, `{other}` in a value are inert).
- There is no escape for a literal brace. Do not write `{` or `}` in a message.
- The French may reorder placeholders: `"{who} wrote {what}"` can become `"{what} a été écrit par {who}"`. The set of names must stay the same.
- Pass numbers you want formatted per locale as `formatNumber(n)` strings; a bare number is `String(n)`. (`tn` formats `{n}` for you.)

## 3. Decisions

### a) How the domain calls `t()`

Domain code (`src/domain/**`) may call `t()`, `tn()` and `msg()` by importing the **pure** `src/i18n/translate.ts`. It has no I/O and no Node or browser API, so it passes the domain purity rule (`eslint.domain-purity.js` forbids `app/`, `adapters/`, `pages/`, `components/`, `astro` and the runtime; it also forbids `src/i18n/fr/**` and `merge-catalogs` so the domain never imports catalog data). No allowance was needed for `src/i18n/translate`; `tests/integration/domain-import-rules.test.ts` proves both the allowance and the ban.

The locale itself is not in the domain. `translate.ts` holds a **resolver function** (`setLocaleResolver`) that answers "which locale now?" on every call:

- server: `src/adapters/i18n/request-locale.ts` backs it with an `AsyncLocalStorage` that the middleware fills per request, and `src/composition.ts` registers it (`installI18n`) once when the module loads, together with the French catalog, strict mode and the "missing translation" logger.
- browser: `src/scripts/i18n.ts` backs it with `document.documentElement.lang`.

Why a resolver and not a hidden global "current locale" variable: a module-level variable set per request would leak one request's language into another that interleaves at an `await`. The resolver is read on every call and the storage is per async chain, which `tests/integration/i18n/request-locale.test.ts` checks with interleaved requests and a streamed response body.

Outside a request (start-up, a background job) the resolver answers with the server default. A job that must write in the owner's language wraps its work in `runWithLocale(locale, fn)` from the adapter. The transcribe and summarize handlers are wrapped once, in `src/composition.ts`, by `withOwnerLocale(handler, languages)` (`src/adapters/i18n/job-locale.ts`): it reads `settings.language` for the job's owner (default locale when unset or unreadable, with an `i18n.locale_unavailable` warning), then runs the handler under `runWithLocale`. Use cases then just call `currentLocale()` / `t()`; see section 15.

### b) A sentence is never built from translated pieces

One sentence, one `t()` with `{params}`. Translating the pieces and joining them makes word order, agreement and punctuation impossible in French.

```ts
// Wrong
t("Next attempt") + ": " + when;
`${t("Saved at")} ${time}`;
t("You have") + " " + n + " " + t("notes");

// Right
t("Next attempt: {when}", { when });
t("Saved at {time}.", { time });
tn("You have {n} note", "You have {n} notes", n);
```

The catalog test flags `+` and template literals that contain a `t()`/`tn()` call (`concatenation`), and a source string that starts or ends with whitespace (`edge-whitespace`, the usual sign of a split sentence). Joining two translated things with a pure separator in the markup (`{t("a")}{" · "}{t("b")}`) is fine: the separator is not a sentence part.

### c) What is never translated

- Identifiers, ids, field and form names, CSS classes, URLs and paths, enum values that travel in URLs or forms.
- Log events and log fields (`job.vocabulary_unavailable`), and error **codes** shown as codes (`llm_unavailable`, `calendar_not_connected`): the code stays; the sentence around it is translated.
- The app name `Willycrumbs`, provider names (Deepgram, Whisper, Anthropic, Claude Code, Google), file names and extensions (`export.md`), the zone code `UTC`.
- Everything the owner wrote or said: titles, notes, folder and template names, template headings, decisions and action items, transcript text, and the words in the vocabulary list.
- The language names in the selector: `English` and `Français` are always shown in their own language (`LANGUAGE_CHOICES`).

### d) Strings that are identical in French

A translation equal to its source fails the test (a forgotten copy looks exactly like this), unless it is allowlisted. The allowlist sits next to the strings, keyed by the English source with a reason, so parallel work does not collide:

```ts
// src/i18n/fr/notes.ts
export const fr: Record<string, string> = { Notes: "Notes", "{n} notes": "{n} notes" };
export const sameInFrench: Record<string, string> = {
  Notes: "Same word in French",
  "{n} notes": "Same word in French",
};
```

A blank reason fails. An entry that is no longer identical (or no longer exists) fails as `stale-allowlist`, so the list only holds live exceptions. Strings with nothing to translate once `{params}` are removed (`"{n}%"`) need no entry.

## 4. Adding a string

1. Write the English in code with `t()` / `tn()`, as the only argument literal: `t("Enter your email and password.")`. Joined literals (`"a " + "b"`) and plain template literals are accepted so prettier can wrap long sentences.
2. Add the French to the area module `src/i18n/fr/<area>.ts` under exactly the same key.
3. Run `npx vitest run tests/unit/i18n`. It names what is missing, unused or inconsistent, with file and line.

Adding a new area module: create `src/i18n/fr/<area>.ts` exporting `fr` and `sameInFrench` (empty is fine), then add it to the `AREAS` object in `src/i18n/fr/index.ts` (one line, and one import). Existing modules: `shell.ts` (page frame), `auth.ts` (sign-in and `src/app/identity`), `settings.ts` (Settings, vocabulary, retention, permanent deletion, error pages), `search.ts` (search and the Markdown export), `scripts.ts` (client, section 6).

The same English string in two areas is allowed if both translate it the same way (a shared "Cancel"); two different translations throw at start-up with both area names. **There is no context mechanism** (no `msgctxt`): if one English word needs two French renderings ("Open" the verb, "Open" the state), make the English sources different on purpose ("Open note" and "Open (status)").

### Messages created in the domain or app layer

Wrap them **where they are created**, with the literal in view, so the result is already a string in the request's language when it reaches the page:

```ts
return err([{ field: "language", message: t("Choose a language from the list.") }]);
```

### Never call `t()` at module top level

A module-level `const MESSAGE = t("...")` runs once, at import, in whatever locale is current then, and every later request gets that language. This also applies to values built at load time: zod schema messages (`z.string().min(1, t("..."))`), arrays of labels, `Record`s. Do one of these instead:

- build the message where it is used (a function, or inside the use case);
- keep the table of **English** strings with `msg()` and call `t()` when showing a value (section 5).

## 5. Tables of labels: `msg()`

```ts
const LABEL: Record<Status, string> = {
  draft: msg("Draft"),
  published: msg("Published"),
};
export const label = (status: Status): string => t(LABEL[status]);   // runs per request
```

`msg("...")` returns its argument unchanged and tells the scanner the literal needs a French entry. The `t(LABEL[status])` call has a non-literal argument, which the catalog test refuses (`non-literal`) unless the file is allowlisted with a reason in `tests/unit/i18n/allowlists.ts` (`allowedDynamic`, path to reason). Prefer a `switch` with a literal `t()` per case when there are only a few values: no allowlist needed. `src/app/settings/notices.ts` is the worked example: an English table of `msg()` texts and one `t(source)` per request in `settingsNotice()` (allowlisted in `allowedDynamic`).

## 6. Client scripts

Entry scripts (`src/scripts/*.ts`) start with `import "./i18n";` (a unit test enforces it). That module registers the **client catalog** and tells the shared core to read the locale from `<html lang>`, which the server sets from the request locale. Domain modules a script imports (for example `src/domain/progress/text.ts`) call the same `t()` and translate in the browser too.

**Bundle decision: per-script catalog, not the whole catalog.** Importing every French string into every script would ship the whole app's French (grows to tens of KB) to pages that show two messages. Instead the browser only gets `src/i18n/fr/scripts.ts`. The catalog test computes every file a client script can reach (its imports, transitively, with the TypeScript compiler API) and requires each `t()`/`tn()`/`msg()` literal in them to be in `scripts.ts` (`client-catalog-missing`), and each entry of `scripts.ts` to be used by one of them (`client-catalog-unused`). Server-only strings never reach the browser: the shared chunk is about 1.2 KB today (`dist/client/_astro/i18n.*.js`). Keep client strings few: send a code and let the server write the sentence when you can.

If a string is shown by both a script and the server, put it in `scripts.ts`; the server catalog includes `scripts.ts` through `fr/index.ts`, so it is not repeated.

## 7. Safety: text nodes only

Translations and the values put into them are text. Astro escapes `{t(...)}`; scripts use `textContent`. Nothing in `src` may parse a string as HTML: `tests/unit/i18n/no-html-sinks.test.ts` fails on `set:html`, `innerHTML`, `outerHTML`, `insertAdjacentHTML`, `document.write` and `dangerouslySetInnerHTML` (an exception needs a path and a reason in that file). `tests/integration/i18n/escaping.test.ts` renders a real Astro component and checks that markup in a value or in a catalog entry comes out escaped. The catalog test also rejects a source or a translation that looks like HTML (`markup`). Do not put tags in a message to bold or link a word: split the markup in the template and keep two messages or a `{param}`.

Transcript and note text is untrusted input to the LLM and is never put through `t()`.

## 8. What the catalog test checks (`tests/unit/i18n/catalog.test.ts`)

It scans `src/**/*.ts` with the TypeScript compiler API and `src/**/*.astro` through Astro's compiler (converted to TSX, so calls inside `{...}` in the template are found), following import aliases (`import { t as tr }`) and namespace imports. A local variable called `t` that is not imported from `translate` is ignored. No build is needed.

| Code | Fails when |
|---|---|
| `missing-translation` | a source string has no French entry |
| `unused-entry` | a French entry matches no `t()`/`tn()`/`msg()` in `src` |
| `param-mismatch` | the `{params}` of source and translation differ (as sets) |
| `identical` | translation equals source, not allowlisted with a reason |
| `stale-allowlist` | an allowlist entry matches nothing (identical, dynamic or concatenation) |
| `empty` | a translation is blank |
| `non-literal` | `t()`/`tn()`/`msg()` first argument is not a literal (allowlist: `allowedDynamic`) |
| `concatenation` | a translated string is joined to other text (allowlist: `allowedConcatenation`) |
| `edge-whitespace` | a source starts or ends with whitespace |
| `markup` | a source or translation looks like HTML |
| `client-catalog-missing`, `client-catalog-unused` | the client catalog disagrees with the client-reachable code |

The scanner and these rules are themselves tested in `tests/unit/i18n/scan-catalog.test.ts` with inline broken fixtures, so a scanner that silently finds nothing cannot make the real test pass.

## 9. Locale and settings

- `settings.language` is `'en'`, `'fr'` or NULL ("not chosen"), added by migration `0004_language.sql` (rollback in `docs/DATA_MODEL.md` section 9). An owner may have no `settings` row at all; saving the language creates it with the retention defaults, and saving retention never touches the language.
- Settings has a "Language / Langue" section (plain form to `POST /settings/language`, CSRF and Origin checked by the middleware, owner from the session, no id in the form). The selector shows `English` and `Français` in their own language whatever the page language, and the label is the same bilingual text in both.
- `WILLY_DEFAULT_LOCALE` (`en` default, `fr`) and `WILLY_I18N_STRICT` (`1`/`0`) are read by `src/adapters/i18n/config.ts`; a bad value stops the server at start-up naming the variable.
- A failing language read never blocks a page: the default is used and `i18n.locale_unavailable` is logged.
- A request that the `auth` middleware answers itself (403, 429, 411/413) is built by `answerInLocale` in `src/middleware.ts`: it resolves the owner's language (or the default) and runs the builder inside it, because `language` runs later. A redirect to sign-in has no text. The 500 page of `observeRequest` is built through `RequestInfo.inRequestLocale`, which re-enters the language `locals.locale` holds (the default when the failure came before it was resolved). JSON error bodies stay codes.
- `<html lang>` follows the locale (`Base.astro`, and `standalonePage` for documents built outside Astro). `standalonePage` takes the already translated title and an HTML body: translate with `t()` where the page is built and escape with `escapeHtml` / `paragraph` (`src/app/platform/standalone-page.ts`); a message never carries markup.

## 10. Dates and numbers

`formatSchedule(startsAtUtc, timeZone, locale?)`, `formatDay(...)` and `formatInstant(iso, locale?)` use `fr-FR` or `en-GB` from `intlLocale(locale)`, defaulting to the request's locale. English output is byte-identical to before (tests assert it). For any new formatter, take `locale: Locale = currentLocale()` and `intlLocale(locale)`; never hard-code `en-GB` or pass `[]`/`undefined` to `Intl` (that is the browser's or server's language, not the page's). Client scripts format with the page locale too (`clockTime` in `src/scripts/capture/notes-autosave.ts`). The French time zone label is `UTC+1` where English says `CET`: that is Intl's wording, not ours.

Not converted yet (it uses fixed English or `en-GB` formats in domain code): `src/domain/notes/action-chips.ts` (review area). Convert it with its area.

The Markdown export follows the request's language: English keeps `2026-11-06 09:00`, French writes `06/11/2026 09:00`; the fixed labels are translated and the owner's text is escaped exactly as before. A file name stays ASCII and identical in both languages.

## 11. Testing in French

```ts
import { inLocale } from "../../support/locale";

const result = inLocale("fr", () => saveLanguage(deps, "A", "klingon"));   // sync or async fn
expect(result).toEqual({ ok: false, error: [{ field: "language", message: "Choisissez une langue dans la liste." }] });
```

`tests/support/locale.ts` registers the French catalog with strict mode on, then runs the function as a French request. Use it for domain, app and component tests; assert French wording only for the strings your area owns.

End to end: the Playwright config builds once and starts two servers from that build, an English one (the default for every spec) and a second with `WILLY_DEFAULT_LOCALE=fr` (base URL in `process.env.E2E_FR_BASE_URL`, data directory `E2E_FR_DATA_DIR`). Both run with `WILLY_I18N_STRICT=1`. To get a French signed-in owner on the English server, **choose Français in the real Settings form** with a fresh owner (`createFreshOwner()` from `tests/support/journey-db.ts`), like `tests/e2e/i18n.spec.ts` does; do not write to the database. `createFreshOwner("fr")` makes an owner on the French-default server, `ownerLanguage(id, server?)` reads the stored choice. Signed-out pages are French only on the second server (`tests/e2e/i18n-fr.spec.ts` and `import { test } from "@playwright/test"` with `test.use({ baseURL: process.env["E2E_FR_BASE_URL"] })`).

Existing English specs keep running on the English server and are untouched by conversions: English output is the source string.

## 12. Strict mode

`WILLY_I18N_STRICT=1`: in a non-English locale a `t()` whose string has no French entry throws `MissingTranslationError` (locale and key in the message, no owner data), the request becomes the usual logged 500 with a request id. English is never affected. Without it the English text is shown and `i18n.missing_translation` is logged once per string (`locale`, `source`). The final crawl package runs every screen in French in strict mode.

## 13. Tone, words and typography

Formal **vous**. Glossary (use these words everywhere, in code comments and tests too when quoting French):

| English (code word) | French |
|---|---|
| Meeting | réunion |
| Note | note |
| Draft | brouillon |
| Published | publiée |
| Folder | dossier |
| Template | modèle |
| Action item | action |
| Decision | décision |
| Attendee | participant |
| Consent | consentement |
| Capture | enregistrement |
| Transcript | transcription |
| Speaker | intervenant |
| Vocabulary | vocabulaire |
| Sign in / Sign out | se connecter / se déconnecter |
| Email | adresse e-mail |

Typography: use the typographic apostrophe `’` (U+2019) in French text, and a no-break space (U+00A0) before `:`, `;`, `?`, `!` and inside `« »`. Sentence case for headings and buttons, like the English. Code, identifiers, logs, docs and commit messages stay English (CLAUDE.md ubiquitous language).

## 14. Converting a screen: checklist

1. Wrap every visible string: headings, labels, buttons, help text, `aria-label`s, `alt`, `title`, the page `<Base title>`, empty and error states, notices.
2. Wrap messages where the domain or app layer creates them. Move any module-level message into a function or use `msg()`.
3. One `t()` per sentence, with `{params}`; plurals with `tn()`.
4. Add the French to your area module; run `npx vitest run tests/unit/i18n`.
5. Dates through the `format-*` helpers (they follow the locale).
6. Leave owner-written text, ids, codes and provider names alone (section 3c).
7. Run the screen in French by choosing Français in Settings, read it, and run the affected e2e specs on desktop and phone. Check that nothing wider than the English breaks the 390 px layout (French is about 15 to 25 percent longer).

## 15. Summaries, templates and transcription (package 6, #122)

- **The summarizer is told the owner's language.** `SummarizerInput.language` (`Locale`) is set by the summary job from `currentLocale()`, i.e. the owner's language under `withOwnerLocale`. `buildSummaryPrompt` turns it into one instruction in `system`: write the summary, decisions and action items in that language, whatever language the meeting used; do not translate the speakers' words; keep each section heading exactly as listed. The language name comes from a fixed table (`src/adapters/llm/language.ts`), so nothing a transcript, agenda, template or vocabulary term says can change it, and the JSON document of untrusted data has no language field. A missing or unknown value falls back to the older rule (the transcript's own language). All adapters (claude-code, Anthropic, fake) share this through `buildSummaryPrompt`/`SummarizerInput`.
- **Default headings per language, for new owners and templates only.** `builtinTemplate()` (`src/domain/notes/template.ts`) returns the built-in layout in the language in force: Summary, Discussion, Next steps / Résumé, Discussion, Prochaines étapes, with prompts in the same language. It is the fallback for an owner with no default template and the starting point of a new template. A template an owner stored keeps the headings they wrote; there is no data rewrite, and changing the interface language never touches stored templates or notes. `DEFAULT_TEMPLATE` stays as the English table of source strings (marked with `msg()`); screens that still list `DEFAULT_TEMPLATE` headings show English until their area switches to `builtinTemplate()`.
- **Transcription language.** `TranscribeRequest.language` carries the same `Locale`. The whisper.cpp adapter uses it for `-l` only when `STT_WHISPER_LANGUAGE` is unset (config `language: null`); a configured value, `auto` included, always wins, and a value that is not one of ours is ignored. The Deepgram adapter does not use the hint yet.
- **Grounding is unchanged**: the model's answer goes through the same schema and source-range checks in every language, and transcript text is never put through `t()`.
